# 접수 창구 단일화

범위: 공통
출처: onmam-dev `docs/discord-incident-intake.md`
상태: 온맘 조정자 확인 전

## 왜

여러 채널에서 아무 말이나 작업으로 바뀌면 같은 일이 두 번 생기고, 회의 대화가 작업으로 새어 나간다. 새 요청이 들어오는 곳을 하나로 정하고, 접수는 이슈를 만드는 데서 멈춘다.

## 규칙

1. 새 장애·요청과 이슈 등록의 창구는 접수 채널 하나다. 상위 일반 채널은 봇 발신·접수를 하지 않는다. 회의실은 접수·발신 대상에서 뺀다(초대 여부에 기대지 않는다).
2. 이슈가 생긴 뒤의 후속 작업과 보고는 그 이슈의 정본 스레드에서만 한다.
3. 접수 담당 실행은 입력(작성자·본문·첨부)을 원장에 보존하고, 중복을 확인한 뒤 이슈만 등록한다. 이 단계에서 제품 코드나 운영 작업을 실행하지 않는다.
4. 접수 담당의 최종 출력은 정해진 한 줄 형식이다: `INTAKE_ISSUE_READY=<저장소>#<번호>`. 실행 장치는 출처, 이슈가 열려 있는지, 스레드를 만들 부모를 확인한 뒤 이슈별 스레드를 만들고 원 요청을 넘긴다. 접수 채널에는 스레드 링크만 남긴다.
5. 후속 작업 식별자는 원 접수 작업에서 결정적으로 만든다. 같은 결과를 다시 처리해도 작업이 늘지 않는다.
6. 스레드 생성 응답을 확인하지 못했으면 정본 이슈로 기존 스레드를 찾는다. 못 찾았다고 새로 만들기를 반복하지 않는다.
7. 번호가 이미 있는 요청은 기존 정본 스레드로 보낸다. 새 이슈 전체를 주기적으로 자동 편입하는 기능은 기본으로 끈다.
8. 발신은 목적지의 실제 정보와 정본 스레드 연결을 검사한 뒤에만 한다. 접근 실패 때 상위 채널로 돌아가 보내지 않는다.

## 확인 항목

- 일반 채널에서 봇을 불러도 작업 0개, 응답 0개.
- 회의실 대화는 접수·발신 안 함.
- 접수 → 이슈 확인 → 이슈별 스레드 생성 → 원문 인계가 한 번씩만 일어남.
- 결과 중복 처리나 생성 응답 불확실 때 작업·스레드가 늘지 않음.
