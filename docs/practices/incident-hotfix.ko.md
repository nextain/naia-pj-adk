# 장애 반영 경로

범위: 공통
출처: onmam-dev `docs/ops/incident-hotfix.md`, `.agents/context/development-process.yaml` (`incident_hotfix_rules`)
상태: 온맘 조정자 확인 전

## 왜

사용자가 지금 못 쓰는 장애를 사람 승인 대기 큐에 넣으면, 승인이 오기 전까지 읽기·준비·대안 조사까지 멈춘다. 장애 경로는 단계마다 시간 한도를 두고, 막히면 정해진 시간 안에 사람에게 닿게 한다. 보통 작업의 경로와 따로 둔다.

## 단계·시간 한도

| # | 단계 | 한도 | 막혔을 때 |
|---|---|---|---|
| 1 | 장애 이슈 번호·대상 파일·후보 리비전을 이슈에 기록 | 5분 | 이슈가 없으면 접수 창구에 등록 요청 |
| 2 | 읽기: 운영 파일 해시·차이, 기준 리비전 조상 여부, 미커밋 변경 수 | 10분 | 아래 "막혔을 때" |
| 3 | 운영 디스크 또는 대상 백업 | 10분 | 승인이 필요하면 같은 행동 |
| 4 | 변경 전 운영 스모크 2회 | 5분 | 실패는 기록하고 기준선으로 씀 |
| 5 | 백업 뒤 최소 단위 반영과 서비스 재적재 | 10분 | 승인이 필요하면 같은 행동 |
| 6 | 변경 후 스모크 2회, 실패 시 백업으로 되돌린 뒤 2회 | 5분 | 되돌리기는 승인 대기 없이 즉시 |
| 7 | 이슈에 리비전·명령·스모크 결과·되돌림 여부 기록, 통합 가지로 같은 변경을 맞춤 | 당일 | |

검증 환경이 없어 사전 검증을 못 하면 대체 증거(통합 환경 같은 리비전 통과, 운영 파일 차이 대조, 단위 시험)를 이슈에 남기고 개발 책임자 확인을 받는다. 확인 전에는 대체 증거를 유효로 치지 않는다.

## 막혔을 때

1. 검사기 차단 원문을 그대로 이슈에 붙인다. 경로 해석 문제처럼 고칠 수 있는 것이면 고쳐서 다시 보낸다.
2. 그래도 막히면 10분 안에 아래 4줄을 개발 책임자에게 개인 메시지와 대시보드로 보낸다.
   ```
   누구: <받는 사람>
   무엇: <막힌 명령 원문 또는 사람이 실행할 한 줄>
   안 하면: <장애가 계속되는 범위>
   기한: <시각>
   ```
3. 도달을 확인한다: 전송 응답과 이슈 기록 링크를 남긴다. 10분 무응답이면 한 번 재촉, 20분이면 두 번째 연락 대상, 40분이면 세 번째 연락 대상에 확인·대행을 요청한다.
4. 기다리는 동안에도 통합·로컬 대조, 공개 주소 읽기, 되돌리기 준비를 계속한다. 대기를 완료로 보고하지 않는다.

## 금지

- 사용자 영향 장애를 사람 승인 대기 큐에 두고 읽기·준비·대안 조사를 멈추는 것.
- 장애 반영을 위해 검사기·승인 스크립트를 우회하는 것.
- 운영에만 있는 수정을 통합 가지에 옮기지 않고 두는 것.

## 적용 방법 (사례마다 정할 것)

- 스모크·재적재·백업 명령, 연락 대상 순서, 개인 메시지 경로.
- 장애 경로에서 쓸 수 있는 읽기 허용 명령 목록(검사기 설정).
