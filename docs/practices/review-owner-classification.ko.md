# 변경 묶음 담당 분류

범위: 공통
출처: onmam-dev `docs/promotion-queue.md` (분류 규칙 절, 보류 표)
상태: 온맘 조정자 확인 전

## 왜

승격할 변경마다 "누가 봐야 하나"를 그때그때 정하면 모든 것이 개발 책임자에게 몰리거나, 반대로 위험한 변경이 자동으로 지나간다. 변경 파일 경로로 담당을 미리 정해 두면 사람 확인은 꼭 필요한 곳에만 간다.

## 담당은 셋

| 담당 | 맡는 일 |
|---|---|
| 개발 책임자 | 인증·보안·데이터 구조와 이전·결제·인프라·운영 쓰기에 닿는 변경의 코드 검토와 승인 |
| 현업 확인자 | 화면·동작에 영향이 있는 변경을 검증 환경에서 보고 기대값과 대조 (무응답 때 넘길 다음 확인자를 사례에서 정함) |
| 자동 | 사람 확인 없음. 자동 검사·시험·문법 검사·스모크 통과 뒤 다음 단계로 |

## 분류 규칙

1. 경로 규칙 표를 우선순위 순으로 둔다. 위에서부터 먼저 맞는 규칙이 담당을 정한다.
   - 1순위 개발 책임자: 서버 설정, 컨테이너·이미지 정의, 데이터 구조 이전 파일, 환경 변수 파일, 인증·권한·복구 코드, 제목에 보안이 들어간 변경.
   - 2순위 현업 확인자: 사용자 화면·앱 코드.
   - 3순위 자동: 문서, 시험, 에이전트 규칙 파일, 자동화 정의, 내용 변경 없는 동기화 병합, 정본과 내용이 같은 묶음, 쓰기 없는 오프라인 도구.
2. 1순위는 고위험 경로에 실제로 걸린 경우에만 이긴다.
3. 분류 불명 칸은 두지 않는다. 경로가 애매하면 코드를 읽고 정하고, 정한 근거를 한 줄 남긴다.
4. 결제 경로는 화면 변경이 섞여도 개발 책임자로 간다.
5. 보류는 고위험 사유가 명시된 것만 둔다(예: 운영 데이터 구조 변경 선행 필요, 되돌릴 수 없는 삭제). 보류 행에는 반드시 "풀리는 조건"을 적는다.

## 적용 방법 (사례마다 정할 것)

- 경로 패턴 목록과 각 담당의 실제 사람·역할 연결.
- 현업 확인자 무응답 때 호출 순서와 기한.
