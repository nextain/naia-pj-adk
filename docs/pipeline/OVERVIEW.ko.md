# 문서 우선 전체 범위 기능 파이프라인

작성일: 2026-09-20  
관련 계약: `.agents/context/development-method.yaml`(변경 분류, 사용자 시나리오, 기능 명세). 이 문서는 그 위에 시험 순서와 영수증 규칙을 사람이 읽는 말로 적는다.  

이 문서는 기능 작업의 **판정 순서**를 정의한다. 문서에 적힌 순서만으로 현재 ADK가 자동 집행된다고 주장하지 않으며, 파이프라인의 범위와 판정 규칙을 기록한다.

## 1. 정본 순서

```text
[PC/SP/UC/RQ/PL/FE 문서 준비·발행 및 digest 기록]
                         │
                         ▼
       [전체 요구 범위 manifest + pre-issue scope lock]
                         │
                         ▼
              [필요 이슈 파생 및 연결]
 (사용자 가치 단위 1이슈 + 체크리스트: 백엔드 UT → 통합 시험(IT) 관문 → UC 기준 화면 구현과 연결 → E2E → 독립 QC)
                         │
                         ▼
        [개발 큐(development queue) 작업 항목 바인딩]
 (여러 저장소에 걸치면 큐 항목을 저장소별 분할, 이슈는 단일 유지)
                         │
                         ▼
       [1단계: 백엔드 구현 및 단위 검증 (UT)]
 (실패 위험이 가장 큰 백엔드 경로를 첫 슬라이스로 선택)
                         │
                         ▼
             [2단계: 통합 시험 (IT)]
  (화면 없이 실제 백엔드 구성요소 관통, 통과 전 화면 확장 금지)
                         │
                         ▼
      [3단계: UC 기준 화면 구현 및 백엔드 연결]
          (화면만 따로 먼저 만들어 넘기지 않음)
                         │
                         ▼
     [4단계: 사용자 여정 관통 시험 (E2E)]
      (실제 화면에서 실제 백엔드까지 전체 경로 관통)
                         │
                         ▼
     [독립 QC: PC/SP 입력만으로 테스트 작성·실행]
                         │
                         ▼
       [모든 manifest 단위의 전체 범위 완료 판정]
```

문서의 출처와 digest, 각 요구사항 단위, 필요한 이슈, 큐 작업 항목, 구현 candidate SHA를 같은 체계로 연결해야 한다. 이 연결을 위해 별도의 수기 완료 목록을 만들지 않는다. `pre-issue scope lock`은 이 자료와 acceptance를 고정하는 진입 기록이다.

문서가 기획 근거·전체 범위·acceptance를 고정하고 `pre-issue scope lock`을 기록하기 전에 이슈나 구현을 시작하지 않는다. 이슈 단계에서 구현 직전에 다시 확인하는 것만으로는 이 순서를 충족하지 못한다. 문서에 검토 중 라벨이 있다는 사실만으로 이미 승인된 작업을 되돌리지 않는다. 최신 결정으로 사용을 승인한 문서와 범위를 명시하고, 그 결정 및 digest를 기록했는지가 이슈 파생보다 먼저 충족되어야 한다.

### 1.1 이슈 전에 고정하는 범위 및 이슈 규칙

`pre-issue scope lock`은 다음 순서로 기록한다.

1. PC/SP/UC/RQ/PL/FE 원문과 현재 digest를 기록한다.
2. 모든 요구사항 단위와 acceptance criterion을 manifest에 펼친다.
3. 각 단위의 `implementation`, `deferred`, `research`, `decision_pending`, `blocked`, `hold` disposition과 owner·근거·재검토/전환 조건을 기록한다.
4. 사람의 범위·acceptance 결정과 manifest/source coverage digest를 고정한다. 범위 잠금의 승인 칸은 반드시 사람(승인자)만 채우며, 인공지능이 임의로 서명하지 않는다.
5. 새 이슈를 만들기 전에 같은 범위의 열린 이슈가 이미 있는지 반드시 검색하고 확인한다.
6. 이 lock이 현재 상태임을 확인한 뒤에만 `implementation` 단위에서 필요한 이슈 세트를 파생·연결한다. 이슈는 사용자 가치 단위 하나에 체크리스트(백엔드 UT → 통합 시험(IT) 관문 → UC 기준 화면 구현과 연결 → E2E → 독립 QC)로 묶으며, 기술 계층(백엔드/화면/시험)별로 이슈를 쪼개지 않는다.
7. 한 이슈의 작업이 여러 저장소에 걸치면(예: 관리 도구 저장소와 사용자 서비스 저장소), 큐 작업 항목은 저장소별로 나누되 GitHub 이슈는 하나로 유지한다. 각 manifest 단위와 이슈의 다대다 연결을 기록한다.

lock이 없거나 만료되면 이슈 생성·연결, 큐 바인딩, candidate 생성, 구현을 모두 차단한다. 이슈 설명에서 새 요구사항이나 acceptance를 임의로 만들지 않는다. 범위나 acceptance가 바뀌면 lock과 manifest를 갱신하고 digest를 다시 고정한 뒤 downstream 이슈·큐·candidate를 재바인딩한다.

### 1.2 기존 이슈의 조정 (reconciliation)

새 문서 우선 규칙을 적용할 때 이미 존재하는 이슈를 삭제하거나 다시 만들거나 생성 시각을 소급하여 변경하지 않는다. 현재 lock 없이 새 이슈·큐·candidate를 만들거나 연결하지 않으며, 기존 기록은 역사 기록으로 보존하고 현재 lock의 source·manifest와 대조하는 별도 reconciliation 경로에 넣는다. 기록에는 원래 이슈 식별자와 생성 시각, 저장소·현재 상태, 연결된 큐 항목·candidate·영수증, 현재 PC/SP/UC/RQ/PL/FE 및 manifest 단위와의 비교 결과를 포함한다. reconciliation이 해결되기 전에는 기존 기록을 현재 범위의 readiness 또는 acceptance 증거로 사용하지 않는다.

각 기존 기록은 `linked`, `rebind_required`, `out_of_scope`, `obsolete`, `blocked`, `decision_pending` 중 하나로 명시적으로 분류한다. 이 분류와 대체 이슈, 사유는 임시 파일이 아니라 반드시 해당 GitHub 이슈 댓글에 직접 남겨 기록을 정정한다. `linked`가 아닌 분류에는 근거·owner·재검토 또는 전환 조건을 기록한다. `rebind_required` 또는 미해결 분류가 남아 있으면 해당 이슈의 이전 큐/candidate 영수증을 새 범위의 증거로 재사용하지 않으며, 구현 readiness와 parent close를 허용하지 않는다. 이슈의 존재·나이·기존 성공 결과만으로 문서 범위나 pre-issue 준수를 추정하지 않는다.

### 1.3 선언과 강제의 구분

이 문서와 워크플로우 명세는 필요한 순서를 선언한다. 문서 선언 자체는 런타임 통과(PASS) 증거가 아니며, 이 절차를 기계적으로 강제하는 도구는 각 인스턴스가 붙인다.

## 2. 트랙과 증거

### 2.1 개발 순서 원칙

- **기획은 위에서 아래로 (Top-down), 개발은 아래에서 위로 (Bottom-up)**: 상위 기획과 화면 설계로부터 요구사항을 정의하되, 개발은 바닥의 동작하는 최소 단위부터 만들고 관통을 확인한 후 점진적으로 확대한다.
- **백엔드 우선 및 얇은 슬라이스**: 첫 슬라이스는 실패 위험이 가장 큰 백엔드 경로로 선정한다. 백엔드 구현과 UT를 마치고, 화면 없이 실제 백엔드 구성요소를 끝까지 관통하는 통합 시험(IT)을 먼저 완료한다.
- **IT 통과 전 화면 확장 금지**: 통합 시험(IT)이 통과하기 전에는 화면 개발을 넓히지 않는다.
- **화면만 먼저 만들어 넘기지 않는다**: 백엔드 연결 없는 화면만 따로 만드는 방식은 통합 단계에서 전면 재개발을 부르므로 금지한다. 통합 시험(IT) 통과 후 사용자 시나리오(UC)를 기준으로 화면을 구현하고 실제 백엔드와 연결한다.
- **통합 관통 순서**: 백엔드 구현과 UT → 통합 시험(IT) 관문 → UC 기준 화면 구현과 연결 → E2E → 독립 QC.

### 2.2 트랙 정보 분리와 검증 증거

개발 트랙에는 PC(Product Concept), SP(Screen Plan), UC(User Scenario), RQ(Requirements), PL(Plan), FE(Feature specification)를 전달한다. 개발 과정에서 백엔드 UT, 통합 시험(IT), E2E 영수증을 각각 명확히 분리하여 기록한다.

- **UT (단위/기능 검증)**: 각 기능 및 백엔드 로직 단위의 명세 검증.
- **통합 시험(IT)**: 화면 없이 실제 백엔드(API, DB, 작업 큐, 모델/엔진)를 관통하는 시험. 정보기술(IT)과의 혼동을 방지하기 위해 각 문서의 첫 등장 시 '통합 시험(IT)'으로 풀어 쓴다.
- **E2E (End-to-End 사용자 여정 관통 시험)**: 실제 브라우저/화면에서 실제 백엔드까지 전체 경로를 끝까지 관통하는 시험. 인정 조건은 실제 화면과 실제 백엔드를 관통했는가이며 접속 주소의 형태가 아니다.
- **완료 조건 및 SP 예외**: implementation 단위는 통합 시험(IT)과 E2E를 모두 갖춰야 완료(close)되고 IT만으로는 닫을 수 없다. 단, 화면이 없는 제품 단위는 E2E가 해당 없음이고 IT로 닫는다. 판정 기준은 구현자의 변경분이 아니라 **화면기획(SP)**이며, SP에 해당 화면이 없는 단위만 E2E 해당 없음(어느 SP 절을 확인했는지 영수증에 근거 명시)이다. SP에 화면이 있는 단위는 이번 변경이 백엔드뿐이어도 E2E가 필요하다.

모든 시험 영수증은 [`TEST-RECEIPT.ko.md`](./TEST-RECEIPT.ko.md)의 정식 양식을 준수해야 하며, 실행한 시험 수·실패 수·종료 코드를 칸으로 두어 실패가 포함된 완료 선언을 방지한다.

QC는 테스트를 작성할 때 PC와 SP만 입력으로 받는다. UC 각본과 FE 내부 구현을 QC 입력에 섞지 않아야 한다. QC가 PC/SP를 기준으로 실제 제품을 실행하고 악의적·경계 입력을 관측하는 것은 이 정보 경계를 위반하지 않는다. QC 결과는 개발자 UT/IT/E2E의 대체물이 아니다.

얇은 수직 슬라이스는 문서·manifest·pre-issue lock·필요 이슈·큐 바인딩 뒤에 실행한다. 구현 중 문서나 범위가 바뀌면 먼저 lock, manifest와 이슈/큐 연결을 갱신하고, 그 candidate에 대해 UT·IT·E2E·QC를 다시 묶는다.

### 2.3 공용 창구 규칙

- 작업 세션은 프로젝트 책임자가 확인하는 공용 창구(공용 포트·운영 주소)를 점유하지 않고 격리된 포트에서 개발 및 시험을 수행한다.
- 프로젝트 책임자에게 실물을 보일 때는 책임자가 실제로 접속하는 공식 경로(외부 접근 경로 등)로 안내한다.

manifest의 각 단위는 사용자와 소유자가 승인한 `implementation`, `deferred`, `research`, `decision_pending`, `blocked`, `hold` disposition 중 하나를 가진다. `deferred`·`research`·`decision_pending`·`blocked`·`hold`는 결정·근거·owner·재검토 또는 전환 조건을 남기지만 구현 PASS나 전체 요청 범위 완료로 계산하지 않는다. 인공지능이 범위를 줄이기 위해 disposition을 임의로 지정하지 않는다.

## 3. 전체 범위 완료 규칙

- `implementation` disposition의 요구사항 단위는 필요한 이슈 세트와 실행 큐 항목에 연결되어야 한다. 한 단위가 여러 이슈를 참조하거나 하나의 이슈가 여러 단위를 덮을 수 있으므로, manifest 단위·이슈·큐 항목 사이의 다대다 연결을 각각 기록하고 검증한다.
- 승인된 `deferred`·`research`·`decision_pending`·`blocked`·`hold` disposition은 즉시 이슈와 큐를 만들 필요가 없지만, 결정·근거·owner·재검토 또는 전환 조건을 기록해야 한다. 인공지능이 범위를 줄이기 위해 disposition을 임의로 정하지 않으며, 구현 PASS나 전체 요청 범위 완료로 계산하지 않는다. 실행으로 전환할 때 이슈와 큐를 만든다.
- `implementation` 단위의 문서 digest, 이슈/큐 상태, 구현 candidate SHA, UT 영수증, IT 영수증, E2E 영수증, 독립 QC 영수증은 현재 작업과 일치해야 한다. implementation 단위는 IT와 E2E를 모두 갖춰야만 닫히며, IT만으로 닫을 수 없다. 단, 화면이 없는 제품 단위(SP에 해당 화면이 없는 단위에 한하며, 어느 SP 절을 확인했는지 영수증에 근거 명시)는 E2E가 해당 없음이며 IT만으로 닫을 수 있다. SP에 화면이 있는 단위는 이번 변경이 백엔드뿐이어도 E2E가 필요하다.
- UT, IT, E2E가 서로 다른 증거로 남아야 한다. IT/E2E가 실행되지 않았거나 백엔드를 사용할 수 없으면 통과(PASS)가 아니다.
- QC 영수증에는 PC/SP 입력 경계와 독립 리뷰어 정보가 있어야 한다. 실제 호출 환경이 준비되지 않아 검증하지 못한 경우에는 사유에 맞게 상태를 남기며 완료로 승격하지 않는다.
- 하위(child) 작업이 완료되어도 상위(parent)의 전체 manifest가 완료되는 것은 아니다.
- 오래된 digest/SHA, 부분 범위, 이전 보고서, 만료된 영수증은 전체 완료 증거가 아니다.
- 미완료 단위가 남아 있으면 상위 완료를 허용하지 않는다.

개발 큐는 구현 작업의 항목·점유(claim)·시작(start)·생존확인(heartbeat)·결과(result)를 보존한다. 결과가 성공이라 하더라도 이는 구현 작업이 끝났다는 뜻일 뿐 독립 QC나 제품 수용을 뜻하지 않는다. 검증 영수증도 동일한 이슈·manifest·candidate에 연결되기 전에는 전체 완료 증거가 아니다.

## 4. 연결 상태 관리

이 절차를 기계적으로 강제하는 도구는 각 인스턴스가 붙인다.
