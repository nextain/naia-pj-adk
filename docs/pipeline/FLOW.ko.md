# 문서·이슈·개발 큐·검증 연결 워크플로우

작성일: 2026-09-20  
표준 정본: `.agents/workflows/issue-driven-development.yaml`

이 문서는 목표 실행 순서를 설명한다. 이 절차를 기계적으로 강제하는 도구는 각 인스턴스가 붙인다.

## 1. 표준 흐름

```text
문서 원문과 결정 기록
  PC + SP + UC + RQ + PL + FE
             │ 발행·digest
             ▼
전체 범위 manifest + pre-issue scope lock
  (사람 승인 칸은 사람만 채움, 새 이슈 전 열린 이슈 검색)
             │
             ▼
  단위별 필요한 이슈 (사용자 가치 단위 1이슈 + 체크리스트: 백엔드 UT → 통합 시험(IT) 관문 → UC 기준 화면 구현과 연결 → E2E → 독립 QC)
             │
             ▼
개발 큐(development queue) (여러 저장소 분할 시 큐 항목 저장소별 분할, 이슈는 단일)
             │ work item / claim / receipt
             ▼
[1단계: 백엔드 구현 및 UT] ──► [2단계: 통합 시험(IT)]
 (실패 위험 가장 큰 백엔드 경로)    (화면 없이 실제 백엔드 관통, 통과 전 화면 확장 금지)
                                              │
                                              ▼
                               [3단계: UC 기준 화면 구현 및 백엔드 연결]
                                   (화면만 따로 먼저 만들지 않음)
                                              │
                                              ▼
                               [4단계: E2E (사용자 여정 관통 시험)]
                                   (실제 화면에서 실제 백엔드까지 전체 경로 관통)
                                              │
                                              ▼
                       독립 QC (PC/SP 입력 경계, 별도 세션/주체)
                                              │
                                              ▼
                                   전체 manifest 완료 판정
```

개발 큐(development queue)의 구현 작업 항목은 제품 저장소와 이슈, 실행 주체 참조, 승인된 수용 기준(acceptance)을 가져야 한다. 구현 작업의 성공 결과는 구현 주체의 실행 결과일 뿐 독립 QC 판정이나 제품 전체 완료가 아니다. 검증 영수증은 별도 단계로 취급하고 동일한 이슈·manifest·candidate SHA에 연결해야 한다.

기존 계약 체계와 작업 영수증, 검토 기록을 연결해 사용하며, 문서만을 위한 별도의 수기 완료 원장이나 임의의 대시보드를 추가하지 않는다.

## 2. 불변 규칙

1. **문서와 범위를 먼저 고정한다.** PC/SP/UC/RQ/PL/FE의 출처와 digest, 전체 요구사항 단위와 acceptance, 각 disposition·owner·전환 조건을 manifest에 기록하고 `pre-issue scope lock` digest를 고정한 뒤 필요한 이슈를 파생한다. 범위 잠금의 승인 칸은 반드시 사람(승인자)만 채우며 인공지능이 임의로 서명하지 않는다. 새 이슈를 만들기 전에 같은 범위의 열린 이슈가 이미 있는지 먼저 검색한다. lock이 없거나 만료되면 이슈·큐·candidate·구현을 만들지 않는다. 검토 중 라벨 하나만으로 최신 사람 결정을 무효화하지 않으며, 승인된 사용 범위와 결정을 기록하지 않은 채 구현으로 진행하지 않는다.
2. **이슈와 큐를 구현 단위에 연결한다.** 이슈는 사용자 가치 단위 하나에 체크리스트(백엔드 UT → 통합 시험(IT) 관문 → UC 기준 화면 구현과 연결 → E2E → 독립 QC)로 묶으며, 기술 계층(백엔드/화면/시험)별로 이슈를 쪼개지 않는다. 한 이슈가 여러 저장소에 걸치면 큐 항목을 저장소별로 나누고 이슈는 하나로 둔다. 각 `implementation` manifest 단위는 하나 이상의 제품 이슈, 개발 큐 항목, 실행 주체, candidate를 가리켜야 한다. `deferred`·`research`·`decision_pending`·`blocked`·`hold` 단위는 사용자와 소유자의 승인과 결정·근거·owner·재검토 또는 전환 조건을 기록하고, 인공지능이 범위를 줄이기 위해 임의로 정하지 않으며 구현 PASS나 전체 요청 범위 완료로 계산하지 않는다. 실행으로 전환될 때 이슈와 작업 항목을 만든다. 이슈나 큐 바인딩이 없으면 구현을 전체 범위 통과로 보고하지 않는다.
3. **개발은 아래에서 위로 진행하고, UT/IT/E2E를 분리한다.** 기획은 위에서 아래로(Top-down), 개발은 아래에서 위로(Bottom-up). 첫 슬라이스는 실패 위험이 가장 큰 백엔드 경로로 선정하며, 백엔드 구현과 UT를 거쳐 화면 없이 실제 백엔드 구성요소를 끝까지 관통하는 통합 시험(IT)을 완료한다. 통합 시험(IT)이 통과하기 전에는 화면을 넓히지 않으며, 화면만 따로 먼저 만들어 넘기지 않는다. 통합 시험(IT) 통과 후 사용자 시나리오(UC) 기준으로 화면을 구현하고 실제 백엔드와 연결하여 E2E를 실행한다. implementation 단위는 통합 시험(IT)과 E2E를 모두 갖춰야 닫히고 IT만으로는 닫을 수 없다. 단, 화면이 없는 제품 단위는 E2E가 해당 없음이고 IT로 닫는다. 판정 기준은 구현자의 변경분이 아니라 화면기획(SP)이며, SP에 해당 화면이 없는 단위만 E2E 해당 없음(어느 SP 절을 확인했는지 영수증에 근거 명시)이다. SP에 화면이 있는 단위는 이번 변경이 백엔드뿐이어도 E2E가 필요하다. E2E의 인정 조건은 실제 화면과 실제 백엔드를 관통했는가이며 접속 주소의 형태가 아니다. 모의 객체(mock/stub)만 거친 것은 IT나 E2E가 아니다.
4. **QC의 입력 경계를 지킨다.** 독립 QC가 테스트를 설계할 때 받는 입력은 PC와 SP다. UC 정상 시나리오나 FE 내부 구현을 QC 입력에 제공하지 않는다. QC가 실행 중인 제품을 공격적으로 관측하는 행위 자체는 금지하지 않는다.
5. **전체 범위로 닫는다.** 하위(child) 작업이 완료되어도 상위(parent)는 모든 manifest 단위가 완료되고 각 단위의 최신 문서·이슈/큐·FE·UT·IT·E2E·QC 증거가 현재 candidate와 일치할 때만 닫힌다. 승인된 `deferred`·`research`·`decision_pending`·`blocked`·`hold` 단위는 결정·근거·owner·재검토 또는 전환 조건을 보존하는 미완료 증거이며 상위 완료를 허용하지 않는다. 만료되거나 부분적인 영수증은 완료 증거가 아니다.
6. **상태를 숨기지 않는다.** 진행 중, 보류, 차단, 미실행 상태를 임의로 성공으로 변환하지 않는다.
7. **공용 창구를 보호하고 프로젝트 책임자 경로로 안내한다.** 작업 세션은 프로젝트 책임자가 확인하는 공용 창구(공용 포트·운영 주소)를 점유하지 않고 격리된 포트에서 시험한다. 프로젝트 책임자에게 실물을 보일 때는 책임자가 실제로 접속하는 공식 경로로 안내한다.

## 3. 생명주기

### 3.1 문서와 pre-issue scope lock

1. PC와 SP로 제품 약속과 화면 표면을 고정하고, 개발에 필요한 UC/RQ/PL/FE를 연결한다.
2. 각 source의 현재 digest와 사람의 사용 결정, 전체 요구사항 단위, acceptance, disposition·owner·전환 조건을 manifest로 기록한다. 범위 잠금의 승인 칸은 반드시 사람만 채운다.
3. source-to-unit coverage와 decision/manifest digest를 `pre-issue scope lock`으로 고정한다. 이 lock은 이슈 단계의 선행 입력이며, 구현 직전에 확인하는 보조 체크가 아니다. 새 이슈 생성 전 같은 범위의 열린 이슈를 먼저 찾는다.
4. 문서 또는 범위가 바뀌면 lock과 manifest, 이후 이슈/큐 연결을 먼저 갱신한다. 이미 실행한 증거는 새 candidate의 증거로 재사용하지 않는다.

#### 역사 이슈의 조정 (historical issue reconciliation)

문서 우선 규칙보다 먼저 생성된 이슈와 큐 기록은 삭제·재생성·시간 소급으로 정리하지 않는다. 새 이슈·큐·candidate는 현재 lock 없이 만들거나 연결할 수 없다. 기존 기록은 원래 식별자·생성 시각·댓글·상태·큐 영수증·candidate 참조를 보존한 채, 현재 lock의 PC/SP/UC/RQ/PL/FE source와 full-scope manifest에 대조하는 reconciliation 경로로만 진입한다. 대조 결과는 `linked`, `rebind_required`, `out_of_scope`, `obsolete`, `blocked`, `decision_pending` 중 하나로 분류한다. 이 분류와 대체 이슈, 사유는 임시 파일이 아니라 반드시 해당 GitHub 이슈 댓글에 직접 남겨 기록을 정정한다. `linked`가 아닌 경우 근거·owner·재검토 또는 전환 조건을 기록한다. reconciliation이 해결되기 전에는 downstream 연결·readiness에 사용하지 않는다.

`rebind_required` 또는 미해결 분류가 있으면 이전 이슈나 이전 작업 결과를 새 범위의 acceptance·source coverage·구현 readiness 증거로 재사용하지 않는다. `linked` 또는 명시적으로 조정된 implementation 단위만 계획·readiness로 이동할 수 있고, 나머지는 상위 완료를 막는다.

### 3.2 이슈와 개발 큐

1. `pre-issue scope lock`이 유효한 `implementation` manifest 단위에서만 필요한 제품 이슈 세트를 만들거나 기존 이슈를 명시적으로 연결한다. 이슈는 사용자 가치 단위 하나에 체크리스트(백엔드 UT → 통합 시험(IT) 관문 → UC 기준 화면 구현과 연결 → E2E → 독립 QC)로 묶고, 기술 계층별 이슈는 만들지 않는다. 공유 이슈를 사용하는 경우에도 각 manifest 단위와 이슈의 다대다 연결을 기록한다. 이슈 본문에서 새 요구사항이나 acceptance를 임의로 파생하지 않는다. 승인된 보류·조사 단위는 실행 전환 전까지 이슈를 즉시 만들지 않고 근거를 보존한다.
2. 개발 큐에 작업 항목을 만들 때 제품 저장소, `owner/repository#number` 형식의 이슈, 실행 주체 참조, 고정된 acceptance를 함께 기록한다. 한 이슈가 여러 저장소에 걸치면 큐 항목은 저장소별로 나눈다.
3. 큐의 정해진 순서인 작업 항목 → 점유(claim) → 시작 영수증 → 생존확인(heartbeat) → 결과 영수증을 따른다.
4. 작업 항목 결과가 성공이라 하더라도 이는 구현 결과일 뿐이다. UT/IT/E2E/QC 영수증과 전체 범위 판정은 별도로 남긴다.
5. 이슈 또는 고정된 acceptance가 바뀌면 lock과 manifest digest를 다시 고정하고 이슈·큐·candidate를 재바인딩한다. 이전 큐 결과는 새 범위의 증거로 재사용하지 않는다.

### 3.3 백엔드 구현과 UT, 통합 시험(IT), 화면 연결, E2E

1. **원칙**: 기획은 위에서 아래로, 개발은 아래에서 위로. 첫 슬라이스는 실패 위험이 가장 큰 백엔드 경로로 선정한다.
2. **1단계: 백엔드 구현 및 UT**: 승인된 문서·manifest·이슈·큐 단위 안에서 백엔드 로직을 구현하고 단위 기능 테스트(UT)를 실행한다. UT를 변경된 코드와 요구 단위에 대해 실행하고, 실행 명령·candidate SHA·결과·영수증 경로를 남긴다.
3. **2단계: 통합 시험 (IT)**: 화면(UI) 없이 실제 백엔드 구성요소(API, DB, 작업 큐, 모델/엔진)를 끝까지 관통하여 검증한다. 목 객체나 스텁만 거친 테스트는 IT가 아니다. **통합 시험(IT)이 통과하기 전에는 화면 개발을 넓히지 않는다.** 환경 또는 백엔드가 준비되지 않으면 미실행/차단으로 둔다.
4. **3단계: 화면 구현 및 백엔드 연결**: 통합 시험(IT) 통과 후 사용자 시나리오(UC)를 기준으로 화면을 구현하고 실제 백엔드와 연결한다. 화면만 따로 먼저 만들어 넘기지 않는다.
5. **4단계: 사용자 여정 관통 시험 (E2E)**: 실제 브라우저/화면에서 실제 백엔드까지 전체 경로를 끝까지 관통하여 검증한다. 인정 조건은 실제 화면과 실제 백엔드를 관통했는가이며 접속 주소의 형태가 아니다.
6. **영수증 양식 및 일치 규칙**: 모든 시험은 [`TEST-RECEIPT.ko.md`](./TEST-RECEIPT.ko.md) 양식을 따라 시험 수·실패 수·종료 코드·대상 저장소/커밋·시험 주소·산출물 경로를 기록한다. 실패가 있는데 완료로 닫는 것을 방지한다. UT와 IT/E2E 영수증에는 같은 manifest 단위와 candidate SHA가 있어야 한다.
7. **완료 및 QC 전 진입 조건**: implementation 단위는 통합 시험(IT)과 E2E를 모두 갖춰야만 닫히며, IT만으로 닫을 수 없다. 단, 화면이 없는 제품 단위는 E2E가 해당 없음이고 IT로 닫는다. 판정 기준은 구현자의 변경분이 아니라 **화면기획(SP)**이며, SP에 해당 화면이 없는 단위만 E2E 해당 없음(어느 SP 절을 확인했는지 영수증에 근거 명시)이다. SP에 화면이 있는 단위는 이번 변경이 백엔드뿐이어도 E2E가 필요하다. 개발 UT/IT/E2E가 고정된 요구사항의 acceptance criterion마다 출처와 결과를 추적한 뒤에야 QC로 넘어간다.

### 3.4 독립 QC

1. QC 작업에는 PC/SP 원문 digest와 candidate/manifest 식별자만 전달한다.
2. QC 작성/실행 주체는 구현 주체와 다른 세션이어야 하며, UC/FE 내부 산출물을 입력에 포함하지 않는다.
3. QC는 실제 제품을 실행해 PC 약속과 SP 표면을 적대적으로 확인할 수 있다. 결과에는 실행 환경, candidate SHA, 입력 digest, 독립 실행 정보, 원시 영수증 경로를 기록한다.
4. 실행 환경이나 자격 증명이 없어 호출하지 못한 경우에는 원인에 맞게 미실행 또는 차단으로 기록하며, 오프라인 진단을 QC 통과로 승격하지 않는다.

### 3.5 전체 범위 판정과 완료

전체 완료는 모든 manifest 단위가 완료되고 각 implementation 단위에 문서 digest, 이슈, 큐 작업 항목/결과, FE candidate, UT, IT, E2E, 독립 QC가 모두 있으며 현재 candidate와 일치할 때만 허용한다. implementation 단위는 IT와 E2E를 모두 갖춰야만 닫히며, IT만으로 닫을 수 없다. 단, 화면이 없는 제품 단위(SP에 해당 화면이 없는 단위에 한하며, 어느 SP 절을 확인했는지 영수증에 근거 명시)는 E2E가 해당 없음이며 IT만으로 닫을 수 있다. SP에 화면이 있는 단위는 이번 변경이 백엔드뿐이어도 E2E가 필요하다. 승인된 보류·대기 단위는 근거를 보존하지만 전체 완료로 계산하지 않는다.
