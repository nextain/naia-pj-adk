# 표준 용어 사전 (Terminology & Communication Policy)

관련 계약: `.agents/context/development-method.yaml`(변경 분류, 사용자 시나리오, 기능 명세). 이 문서는 그 위에 시험 순서와 영수증 규칙을 사람이 읽는 말로 적는다.  
적용 범위: 워크스페이스 전역 (문서, 코드 주석, PR/이슈, 회고)

## 1. 개발 방법론 약어 정의

> 💡 **핵심 원칙**:
> - **기획은 위에서 아래로 (Top-down), 개발은 아래에서 위로 (Bottom-up)**: 동작하는 최소 단위를 만든 후 확대합니다.
> - **첫 슬라이스는 실패 위험이 가장 큰 백엔드 경로**이며, 그 통합 시험(IT)이 통과하기 전에는 화면을 넓히지 않습니다.
> - **화면만 따로 먼저 만들어 넘기지 않습니다** (백엔드 개발자나 통합 개발자가 전면 재개발하는 낭비 방지).
> - **진행 순서**: 백엔드 구현과 UT → 통합 시험(IT) 관문 → UC 기준 화면 구현과 연결 → E2E → 독립 QC
> - **implementation 단위 완료 조건**: implementation 단위는 IT와 E2E를 모두 갖춰야 닫히며, IT만으로는 닫을 수 없습니다. 단, 화면이 없는 제품 단위는 E2E가 해당 없음이고 IT로 닫습니다. 판정 기준은 구현자의 변경분이 아니라 **화면기획(SP)**이며, SP에 해당 화면이 없는 단위만 E2E 해당 없음(어느 SP 절을 확인했는지 영수증에 근거 명시)입니다. SP에 화면이 있는 단위는 이번 변경이 백엔드뿐이어도 E2E가 필요합니다.

| 용어 (약어) | 한국어 풀이 | 본질적 의미 (Means) | 아닌 것 (Not) |
|---|---|---|---|
| **PC** | Product / Project Concept (상위기획) | **우리가 왜 만드는가.** 제품 또는 핵심 프로젝트의 본질, 존재 이유, 사용자 가치, 전체 정보 구조(IA) 및 소유권 경계. 개발자·기획자·QC 모두가 첫날부터 공유하는 북극성. | 세부 기능 목록이나 기술 스펙이 아니다. |
| **SP** | Screen Plan (화면기획 / 스토리보드) | **사용자가 보게 될 공간과 도면.** 화면 레이아웃, 와이어프레임, 컴포넌트 시각 배치, 화면 간 이동 플로우. 기획·개발·QC가 같은 시각적 실체를 공유하는 기준. | 디자이너의 최종 픽셀 그래픽이 아니라 구조적 도면이다. |
| **UC** | User Scenario (유저 시나리오 / 여정) | **사용자의 맥락과 동기, 엔드투엔드 경험 스토리.** 사용자가 어떤 상황에서 들어와 목표를 달성하고 나가는지의 전체 여정. | 단일 화면 안에서 버튼 누르는 미시적 UI 설명이 아니다. |
| **RQ** | Requirements (요구사항 정의) | **UC와 SP를 만족하기 위해 시스템이 충족해야 할 조건.** 기능 요건, 비기능 요건(지연시간, 리소스, 보안), 측정 가능한 수용 기준(Acceptance Criteria). | 단순 희망 사항이 아니라 검증 가능한 기준이어야 한다. |
| **PL** | Plan / Architecture (기술 분석 및 계획) | **기술적 현실을 검증하고 아키텍처와 단계별 구현 로드맵을 수립하는 것.** | 검증되지 않은 가정이 아니라 실제 코드 기반 계획이다. |
| **FE** | FEature (기능 명세) | **UC와 RQ를 실현하기 위해 무엇을 만들 것인가의 구체적 기능 단위.** | ⚠️ **Frontend가 아니다.** 프론트엔드를 뜻하려면 '프론트엔드'라고 풀어 쓴다. |
| **UT** | Unit & Feature Test (단위 기능 검증) | FE(기능 단위)가 명세대로 동작하는지 검증하는 단위/기능 테스트 (Verification). | 모의 객체만 돌리는 가짜 테스트가 아니다. |
| **IT** | Integration Test (통합 시험) | **화면(UI) 없이 실제 백엔드 구성요소(API, DB, 큐, 워커, 엔진)를 끝까지 관통하여 동작을 검증하는 시험.** 정보기술(IT)과 혼동을 방지하기 위해 각 문서의 첫 등장 시 '통합 시험(IT)'으로 풀어 씁니다. 실패 위험이 가장 큰 백엔드 경로가 첫 슬라이스가 되며, IT가 통과하기 전에는 화면을 넓히지 않습니다. | 실제 서비스 구성요소 없이 mock/stub만 거쳐 통과시키는 시험은 IT가 아니다. |
| **E2E** | End-to-End Test (사용자 여정 관통 시험) | **UC(사용자 여정)를 기준으로 실제 화면에서 실제 백엔드까지 전체 경로를 끝까지 관통하여 검증하는 시험.** implementation 단위는 IT와 E2E를 모두 갖춰야 닫힙니다. 단, 화면이 없는 제품 단위(SP에 해당 화면이 없는 단위에 한하며, 어느 SP 절을 확인했는지 영수증에 근거 명시)는 E2E가 해당 없음이며 IT만으로 닫을 수 있습니다. SP에 화면이 있는 단위는 이번 변경이 백엔드뿐이어도 E2E가 필요합니다. E2E의 인정 조건은 실제 화면과 실제 백엔드를 관통했는가이며 접속 주소의 형태가 아닙니다. | ⚠️ 실제 백엔드 연결 없는 목업 바인딩이나 화면 컴포넌트 렌더링은 E2E가 아니다. IT 영수증 없이 단독으로 완료될 수 없다. |
| **QC** | Quality Control (독립 적대적 타당성 확인) | 개발자의 각본(UC)에 오염되지 않고, 오직 PC(제품 헌장)와 SP(화면 도면)만을 기준으로 '진짜 사용자 가치에 부합하는가', '동의 철회나 억지 입력에도 안전한가'를 가차 없이 찌르는 독립 적대 관문 (Validation). | 개발자 각본(UC)을 따라가는 2차 검증이 아니다. |
| **드리프트 (drift)** | 소스-실제 어긋남 | 소스(git)와 실제(서버·운영)가 어긋난 상태. 반복 사고의 공통 뿌리. | 정상적인 차이가 아니라 즉시 격리·해소해야 할 위험이다. |

## 2. 제품(Product) ⟷ 프로젝트(Project) ⟷ 물리 디렉터리(projects/) 위계 정의

워크스페이스 내의 개념적 위계와 물리적 파일시스템 배치를 명확히 구분합니다:

| 개념 구분 | 본질적 의미 (Means) | 구체적 사례 | 범위 및 소유권 |
|---|---|---|---|
| **Product (제품 / 플랫폼)** | 사용자에게 최종 가치를 제공하고 고유한 대외 브랜드를 갖는 **완성형 서비스·플랫폼** | 예: 사내 포털 서비스<br>예: 고객 지원 플랫폼 | 단일 깃 레포일 수도 있고, 복수 깃 레포(웹 + 앱 + 백엔드)의 연합일 수도 있습니다. |
| **Project (엔지니어링 과제)** | 특정 목적이나 기능을 달성하기 위해 수행하는 **기획·설계·개발 과제 단위** | 예: 결제 기능 개편 과제<br>예: 알림 시스템 구축 과제 | 단일 컴포넌트 내부 작업일 수도 있고, 여러 컴포넌트에 걸친 연합 과제일 수도 있습니다. |
| **projects/ (물리 디렉터리)** | Git으로 관리되는 독립 코드베이스/서브모듈들이 놓이는 **최상위 물리 폴더** | `projects/portal-web`<br>`projects/portal-api`<br>`projects/notification-service` | **업계 표준 관례(Multi-root Workspace)**이며, 시스템 전역 경로 안정성을 위해 **절대 이름을 변경하지 않습니다.** |

> 💡 **핵심 정리**: `projects/`라는 물리 폴더명이 존재한다고 해서, 모든 제품(Product)과 과제(Project)를 무조건 새로운 깃 레포로 쪼개야 함을 의미하지 않습니다.

## 3. 용어 사용 3원칙

1. **표준 용어는 그대로 사용:** AI, LLM, API, STT, TTS, E2E, SQLite, librosa 등 업계 표준 용어는 원문 그대로 유지.
2. **학계 용어는 한국어 풀이 + 영문 병기:** 첫 등장 시 `한국어 풀이 (영문/약어 + 출처)` 형식 (예: `주관 청취 점수 (MOS, 1-5)`, `선행 예측기 (look-ahead predictor)`).
3. **우리만의 신조어 금지:** 발견 즉시 표준 용어로 교체 (예: 외부 AI 4종 교차 검증 등 표준 표현 사용).
