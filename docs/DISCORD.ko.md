# Discord 기반 협업 설계

프로젝트마다 Discord 앱은 하나만 둡니다. 게이트웨이는 팀 개발 서버에서 한 프로세스만 봇 토큰을 소유합니다. 여러 작업공간이 같은 토큰으로 Discord 연결을 직접 열지 않습니다.

공용 채널에서는 GitHub 이슈마다 스레드 하나를 사용합니다. 봇은 이슈 번호로 스레드와 작업을 연결하며, 멘션된 경우에만 응답합니다. 메시지 작성자는 `[별칭/프로젝트]`로 표시합니다. 별칭과 실제 Discord ID의 연결은 추적하지 않는 런타임 등록부에 둡니다.

개인 DM은 발신자의 등록 정보를 이용해 개인 SSH 작업공간을 선택할 수 있습니다. 하지만 DM은 병합·배포·DB 권한을 주지 않습니다. 코딩은 선택된 SSH 작업공간에서 Codex 또는 Claude가 수행하고, 결과는 GitHub 이슈에 남깁니다.

참여자 등록부는 `schemas/participants.schema.json` 형식을 따르며 `.runtime/participants.json`에 둡니다. 저장소에는 형식만 두고 실제 Discord ID, 사용자 계정, 작업공간 경로는 커밋하지 않습니다. 별칭은 프로젝트 안에서 중복될 수 없고, 한 발신자는 한 기본 작업공간으로만 연결합니다. 연결이 없거나 중복되면 봇은 추측하지 않고 등록 요청을 반환합니다.

게이트웨이의 책임은 다음뿐입니다.

- Discord 메시지 수신과 발신자 식별
- 이슈 및 스레드 연결
- 등록된 작업공간으로 작업 요청 전달
- 작업 ID와 결과 요약 반환
- GitHub 이슈에 기록할 근거 링크 제공

게이트웨이가 직접 운영 권한을 가지면 안 됩니다. 배포 명령은 프로젝트별 역할 정책과 `ops_profile`을 별도로 검사해야 합니다. 트래픽 위험이 높지 않은 운영 읽기와, 사용자가 인식하는 비크리티컬 장애 배포를 승인 요청으로 바꾸어 스레드를 멈추면 안 됩니다. 봇이 답해야 하는 침묵을 전문 개발자나 배포 담당자 DM으로 올리지 않습니다. 동일 토큰의 두 번째 소비자가 발견되면 먼저 실행 중인 인스턴스를 추측해 종료하지 말고, 새 인스턴스가 실패 종료해야 합니다.

## Ubuntu VM에서 Codex 준비

Codex는 게이트웨이를 실행할 전용 일반 사용자로 로그인합니다. root 인증정보를 만들지
않습니다. Ubuntu에서는 샌드박스 전제 조건과 Codex CLI를 설치한 뒤 그 사용자 세션에서
장치 로그인을 완료합니다.

```bash
sudo apt-get update
sudo apt-get install -y bubblewrap
sudo npm install -g @openai/codex
sudo -iu <project-user> codex login --device-auth
sudo -iu <project-user> codex login status
```

`codex login status`의 성공을 확인하기 전에는 게이트웨이를 설치하지 않습니다. Discord
토큰과 GitHub 자격 증명은 각각 소유자 전용 런타임 파일에 두고 권한을 `0600`으로
제한합니다. 토큰, 실제 사용자 ID, 호스트명과 IP는 Git에 기록하지 않습니다.

## 게이트웨이 설치와 전환

기존 호스트가 같은 봇 토큰을 사용 중이면 다음 순서를 지킵니다.

1. 기존 서비스 상태와 되돌리기 명령을 기록합니다.
2. 기존 소비자를 정지합니다.
3. VM에 소유자 전용 설정과 토큰을 설치합니다.
4. VM 서비스를 설치하고 서비스·독립 감시 타이머가 모두 활성인지 확인합니다.
5. Gateway 재개 상태와 heartbeat 응답을 확인합니다.
6. 실패하면 VM 서비스를 정지하고 기존 소비자를 복구합니다.

프로세스 실행만으로 성공이라 하지 않습니다. Discord Gateway의 연결 재개 정보와 최근
heartbeat 응답이 함께 있어야 전환이 완료된 것입니다.

## 정기 수집물의 승인 쓰레드

정기 수집 작업은 승인 가능한 후보 상태에서 멈추고 지정된 검수 쓰레드에 후보 ID, 공식
원문, 요약과 정확한 승인·제외 명령 형식을 게시합니다. 응답이 없으면 보류하며 자동 승인하지
않습니다. 쓰레드 명령은 등록된 운영자의 명시적 응답만 받아 후보 ID, 현재 상태, 사유,
저장소의 현재 버전과 쓰레드 바인딩을 검사합니다.

승인은 검수 상태 변경일 뿐 공개·Git 병합·배포 권한이 아닙니다. 공개 반영은 별도의 Git
검토와 배포 승인을 거칩니다. 동시에 바뀐 후보는 덮어쓰지 않고 실패시켜 다시 검토합니다.
