# 2차 적대 검수 — 외부 운영 경험이 공개 계약으로 제대로 추상화됐는가

검수 기준은 문서가 아니라 **실제 실행에서 재현되는 것**입니다. 운영 자료에서 추출한 실패 모양을 공개 계약·검증 명령과 대조하되, 원자료·식별자·운영 위치는 이 저장소에 옮기지 않았습니다.

## 한 줄 결론

**조정과 권한 계층은 충실히 옮겨졌고, 실행과 검증 계층은 옮겨지지 않았습니다.**

초기 후보는 "누가 무엇을 할 수 있는가"를 잘 정했습니다. 그런데 운영에서 사고를 실제로 막는 것은 역할표만이 아니라 **거절하는 실행 명령**입니다. 그 부분이 빠져 있었습니다.

## 잘 옮겨진 것

이 부분은 그대로 두는 것이 맞습니다.

**권한이 도구에서 오지 않는다는 규칙.** `access_to_discord_or_ai_tool_never_grants_operational_authority` 는 실제 운영에서 사고를 막는 경계입니다. 채널 메시지로 보안 가드를 자가 우회하려는 시도는 이 경계에서 멈춰야 합니다.

**Discord 위상.** 프로젝트당 앱 하나, 토큰당 소비자 하나, 중복 시 실패 종료. 같은 토큰을 두 게이트웨이가 물면 응답이 갈라지고 어느 쪽이 처리했는지 알 수 없게 됩니다.

**비밀 취급.** `tracked_files_must_not_contain` 에 개인 ID·사설 호스트·IP·운영 토폴로지까지 넣은 것, 런타임 등록부를 추적에서 뺀 것, 공개 검사 범위에 **도달 가능한 Git 이력**을 포함한 것이 핵심입니다. 평문 자격증명이 이력에 남으면 공개 전에 회전·분류해야 합니다.

**이슈가 정본이라는 구조.** 상태 기계는 내부적으로 정합합니다. 선언되지 않은 상태를 참조하는 전이도, 도달 불가능한 상태도 없습니다.

**스스로에 대한 정직함.** 1차 검수 기록이 독립 교차 검수를 `NOT_RUN` 으로 남긴 것은 좋은 신호입니다. 하지 않은 것을 했다고 적지 않았습니다.

## 빠진 것 — 하나씩

### 1. 게이트가 문서로만 존재했다

배포기는 아무것도 바꾸기 전에 네 가지를 검사하고 **0이 아닌 값으로 끝나야 합니다.** 이슈가 열려 있는가, 작업 트리가 깨끗한가, 통합 브랜치가 내 브랜치의 조상인가, 통합 브랜치와 다른 변경이 있는가.

이 저장소에는 그에 대응하는 것이 없었습니다. `workflow.yaml` 은 `requires: [commit_sha, changed_scope, rollback_plan]` 처럼 **기록해야 할 항목**을 나열합니다. 기록은 잘 쓸 수 있습니다. 망가진 배포에 대해서도 잘 쓸 수 있습니다.

세 번째 조건이 특히 그렇습니다. 통합 브랜치를 담지 않은 브랜치를 배포하면 그 사이의 모든 변경이 조용히 되돌아갑니다. 이 조건이 실행 단계에서 배포를 거절해야 합니다.

**조치:** `execution.yaml` 에 `deploy_gate` 를 넣고, 어댑터 템플릿에 `deploy_gate_command` 자리를 만들었습니다. `null` 이면 그 대상에 배포할 준비가 안 된 것으로 정의했습니다.

### 2. 반영 단계가 없었다

파일을 쓰는 것과 변경이 효력을 갖는 것은 다른 사건입니다. 일부 런타임은 파일을 바꿔도 프로세스를 재적재하기 전에는 옛 코드를 계속 실행합니다. 이 단계를 빠뜨리면 장애가 이어질 수 있습니다.

엣지 캐시도 같습니다. 고친 뒤에도 옛 실패 응답이 계속 나갑니다.

**조치:** `propagation` 을 넣고 환경별로 재적재 명령, 캐시 무효화, 그리고 **새 리비전이 서빙 중임을 증명하는 명령**을 선언하게 했습니다. 앞의 둘은 시도이고 마지막 하나만 증거입니다.

### 3. "검증"이 정의되지 않은 채 이름만 있었다

`local_validation`, `dev_validation`, `post_deploy_validation` 은 필드명이지 정의가 아닙니다. 무엇을 통과로 볼지 적혀 있지 않으면 각자 다른 것을 통과로 봅니다.

운영의 교훈은 구체적입니다. 죽은 서비스가 성공 상태 코드와 오류 본문을 함께 반환할 수 있고, 상태 코드만 보는 감시는 그것을 놓칩니다. 그래서 본문 크기와 필수 문자열까지 단언하고 종료코드로 판정합니다.

**검수 중에 같은 결함을 다시 발견했습니다.** 통합 배포 스크립트가 스모크 실패를 출력하고도 성공으로 끝나거나, 이슈에 통과 문구를 **고정 문자열로** 적으면 안 됩니다. 교훈이 있어도 도구가 강제하지 않으면 되돌아옵니다.

**조치:** `verification` 에 최소 단언 세 가지, 종료코드 판정, 2회 연속, 그리고 단독 증거로 인정하지 않는 목록을 명시했습니다.

### 4. 롤백이 문장이었다

`rollback_plan`, `rollback_reference` 는 이슈에 적는 항목입니다. 실증 프로젝트는 변경 **전에** 되돌릴 물건을 만들어 둡니다. 설정 백업 파일, 이미지 태그, 원본 파일 사본입니다.

문장으로 쓴 롤백은 필요한 순간에 틀렸다는 것을 알게 됩니다.

**조치:** `rollback.must_be_materialized_before_change: true` 와 인정하는 형태 세 가지를 명시했습니다.

### 5. 단일 변경자 개념이 없었다

역할은 있는데 동시성 계약이 없었습니다. 실증 프로젝트는 운영 변경에 임대를 요구하고 만료를 **자동 해제가 아니라 경보**로 취급합니다. 자동으로 풀리는 임대는 두 사람이 같은 환경을 동시에 바꾸도록 초대합니다.

**조치:** `concurrency` 를 넣었습니다.

### 6. 드리프트를 볼 방법이 없었다

운영 코드 저장소가 통합 브랜치보다 뒤처지거나 작업 브랜치가 오래 멈추고, 스테이징 계층이 이름만 남을 수 있습니다. 이런 드리프트는 비교 명령 없이는 발견되지 않습니다.

셋 다 아무도 모르고 있었습니다. 비교하는 명령이 없었기 때문입니다.

**조치:** `drift` 를 넣고, 불일치 시 0이 아닌 값으로 끝나는 비교 명령을 요구했습니다.

### 7. 계층이 호스트 이름으로 이해되고 있었다

템플릿에 `development.url`, `production.url` 만 있었습니다. 계층은 주소가 아니라 **소스와 데이터의 짝**입니다. 통합 계층이 다른 계층과 데이터 소스를 공유할 수도 있으므로, 그 사실을 모르고 데이터베이스를 바꾸면 계층이 무엇을 증명하는지가 통째로 바뀝니다.

그리고 도달할 수 없는 계층은 계층이 아닙니다. 리다이렉트로 바뀐 스테이징은 있다고 믿는 검증 단계를 비워 놓았습니다.

**조치:** `tiers` 를 템플릿에 넣고 계층마다 소스 출처·데이터베이스·배포 권한자를 선언하게 했습니다.

### 8. 산출물 계약이 없었다

신뢰 경계를 넘는 소스는 그대로 옮기지 않고 **검사 후 반입**하며, 커밋된 리비전을 통합 계층으로 내보내 불변 산출물을 만들고 대상을 교체합니다. 서버에 소스를 마운트하지 않습니다.

이 저장소의 `workspace.ssh_home_pattern` 은 개발자 작업공간을 위한 값입니다. 배포 대상까지 서버 소스를 직접 편집하는 방식으로 사용하면 산출물 계보를 잃습니다.

**조치:** `artifact` 에 커밋된 리비전 빌드, 서버 소스 마운트 금지, 신뢰 경계 통과 시 반입 검사를 넣었습니다.

## 이 저장소 자체의 결함

### 검사기가 자기 주장을 검사하지 않았다

1차 검수는 "AI 도구별 규칙이 달라짐 → 바이트 동일성 검사"로 해결했다고 적었습니다. 실제로는 `CLAUDE.md`, `GEMINI.md` 두 개만 검사하고 **`CODEX.md` 는 검사 대상이 아니었습니다.**

`CODEX.md` 는 드리프트가 아니라 의도된 포인터 파일이었습니다. 그러나 검사기가 그 내용을 전혀 보지 않으므로, 앞으로 누군가 거기에 `AGENTS.md` 와 모순되는 규칙을 적어도 아무것도 잡지 않습니다. 실증 프로젝트에서 코덱스가 주 도구라는 점을 생각하면 빈 곳이 잘못된 쪽에 있었습니다.

**조치:** 포인터 계약으로 검사합니다. `AGENTS.md` 를 지목해야 하고, 규칙을 직접 서술할 만큼 길어지면 실패합니다.

### 도구 상태가 추적될 수 있었다

검수 중 하네스가 `.agents/session-contracts/.recovery/leases/` 아래에 실행 상태 파일을 만들 수 있었습니다. 이 파일에는 세션·프로세스·실행 위치 정보가 들어갈 수 있습니다.

`.gitignore` 에 그 경로가 없으면 다음 사람이 `git add -A` 할 때 실행 위치 정보가 이력에 들어갈 수 있습니다. `tracked_files_must_not_contain` 이 금지하는 종류입니다.

**조치:** `.gitignore` 에 하네스·세션 상태 경로를 넣고, 검사기가 그 규칙의 존재를 확인합니다.

### 검사기가 상태 기계를 검사하지 않았다

`workflow.yaml` 은 지금 정합하지만, 우연히 그렇습니다. 선언되지 않은 상태로 전이하거나 정책에 없는 역할을 `actor` 로 적어도 검사기가 통과시켰습니다.

**조치:** 상태 참조와 역할 참조를 교차 검사합니다.

## 검사기가 실제로 잡는지 확인

새로 넣은 검사를 하나씩 깨뜨려 봤습니다. 통과만 확인한 게이트는 통과만 하는 게이트일 수 있습니다.

| 깨뜨린 것 | 결과 |
|---|---|
| 완료 규칙을 `false` 로 뒤집기 | 잡음 |
| 실행 계약 섹션 하나 삭제 | 잡음 |
| 정책에 없는 역할을 `actor` 로 | 잡음 |
| 선언 안 된 상태로 전이 | 잡음 |
| `CODEX.md` 에 규칙 직접 서술 | 잡음 |
| `CODEX.md` 가 `AGENTS.md` 미지목 | 잡음 |
| 템플릿에서 배포 게이트 항목 제거 | 잡음 |
| `.gitignore` 에서 세션 상태 제외 제거 | 잡음 |

8건 전부 0이 아닌 종료코드로 걸렸습니다.

> 첫 시도에서는 8건 전부 "못 잡음"으로 나왔습니다. 검사 스크립트를 파이프로 넘겨 **파이프 마지막 명령의 종료코드**를 읽고 있었기 때문입니다. 이 계약이 종료코드를 판정 기준으로 못박는 이유가 그것이고, 그 함정에 검수자 본인이 먼저 걸렸습니다.

## 3차 — 1차 조치분을 다시 공격했습니다

앞의 조치는 제가 만든 것이고 아무도 검수하지 않았습니다. 같은 기준으로 제 추가분을 공격했더니 다섯 건이 나왔습니다.

### 공개 게이트가 거의 아무것도 잡지 못했습니다

가장 심각합니다. `public-safety-scan.mjs` 는 이 저장소를 공개해도 되는지 판정하는 게이트인데, **저는 그것을 한 번 돌려 보고 "통과"라고 보고했습니다.** 실제로 무엇을 잡는지는 확인하지 않았습니다. 제가 남을 비판한 바로 그 패턴입니다.

열두 가지를 심어 봤습니다. **열 가지가 통과했습니다.**

| 심은 것 | 1차 | 강화 후 |
|---|---|---|
| IPv4 주소 | 잡음 | 잡음 |
| `password=` 리터럴 | 잡음 | 잡음 |
| IPv6 주소 | 통과 | 잡음 |
| 사설 호스트명 | 통과 | 잡음 |
| 일반 `token:` | 통과 | 잡음 |
| `api_key` / `client_secret` | 통과 | 잡음 |
| AWS 액세스 키 | 통과 | 잡음 |
| Discord 봇 토큰 | 통과 | 잡음 |
| 한국어 라벨 비밀번호 | 통과 | 잡음 |
| Bearer·JWT | 통과 | 잡음 |
| 개인 Discord ID | 통과 | 잡음 |
| SSH 공개키·URL 내 자격증명 | 통과 | 잡음 |

패턴을 넷에서 열여섯으로 늘리고, 커밋 메시지까지 검사 범위에 넣고, 사람이 판단한 예외를 `public-safety-allow:` 표식으로 남기게 했습니다. 열네 건을 다시 심어 전부 걸리는 것을 확인했습니다.

이 게이트가 통과한다는 사실만으로 공개를 결정하면 안 됐습니다. **게이트는 무엇을 잡는지 확인한 만큼만 게이트입니다.**

### "null 이면 준비 안 됨" 규칙이 강제되지 않았습니다

실행 계약을 넣으면서 "명령이 `null` 이면 그 대상에 배포할 준비가 안 된 것"이라고 정의했습니다. 그런데 검사기는 **템플릿에 그 키가 있는지만** 봤습니다.

자리표시자가 그대로 남고 모든 명령이 `null` 인 어댑터를 만들어 넣었더니 그대로 통과했습니다. 제가 고치려던 결함을 제가 다시 만든 것입니다. 문서에만 있는 규칙은 규칙이 아니라는 말을 쓰면서요.

이제 `projects/` 아래 활성 어댑터를 검사합니다. 자리표시자가 남아 있으면 거부하고, `reachable: true` 인 계층을 선언했는데 배포 게이트·드리프트·검증 명령이 비어 있으면 거부합니다.

### 절 이름 검사가 부분 문자열이었습니다

실행 계약과 개발 방법의 필수 절을 `includes()` 로 확인했습니다. 그래서 `concurrency:` 를 `x_concurrency:` 로 바꿔도 통과했습니다. 부분 문자열이 남아 있으니까요.

줄 앞에 고정하는 검사로 바꿨고, 네 건을 다시 깨뜨려 전부 걸리는 것을 확인했습니다.

### 환경 선언을 제가 두 곳으로 쪼갰습니다

계층 개념을 넣으면서 `tiers` 를 추가했는데 기존 `environments` 를 그대로 뒀습니다. 데이터베이스 이름이 **두 곳에서 선언**되는 상태가 됐습니다. 한쪽만 바뀌는 것이 드리프트인데, 드리프트 방지 절을 쓰면서 드리프트 벡터를 심었습니다.

`environments` 를 없애고 주소까지 `tiers` 로 모았습니다. 계층마다 `reachable` 도 함께 선언하게 했습니다. 도달할 수 없는 계층은 계층이 아니라는 규칙을 검사 가능한 값으로 만든 것입니다.

### 참여자 등록부의 두 불변식이 검사되지 않았습니다

`discord.yaml` 은 별칭이 프로젝트 안에서 유일하고 발신자마다 기본 작업공간이 하나라고 선언합니다. JSON 스키마는 둘 다 표현할 수 없고, 다른 무엇도 검사하지 않았습니다.

중복되면 먼저 나온 행으로 해석됩니다. 신원 문제인데 라우팅 문제처럼 보이는 종류의 버그입니다. `scripts/validate-participants.mjs` 를 만들어 두 불변식과 스노플레이크 형식까지 검사하고, 여덟 가지 입력으로 시험했습니다.

## 개발 방법의 앞부분이 통째로 빠져 있었습니다

검수의 질문은 "한 운영 프로젝트의 **개발 방법**을 추상화해서 제대로 이식했는가"였습니다. 배포와 검증만 보고 그 앞을 놓쳤습니다.

운영 프로젝트의 개발 방법은 용어에서 시작합니다. 용어 → UC(사용자 시나리오) → UC 테스트 → FE(기능) → FE 테스트 → 구현 → 검증. 이 체인 전체가 이 저장소에 없었습니다.

빠져 있던 것들입니다.

**용어가 0번 축이라는 것.** 정의 없는 약어를 추측하면 범위와 시험과 검토를 거쳐 전파되는데 어느 단계에서도 이상해 보이지 않습니다. 운영 자료에서 `FE` 를 Frontend 로 읽었는데 실제로는 Feature 였고, 추측 하나에서 명세 전체가 어긋났습니다.

**변경의 크기를 배정 전에 정한다는 것.** 13장이 적은 문제가 정확히 이것입니다. 큰 작업을 받은 작업자가 바로 구현부터 시작해 일부만 고치고 전체를 끝냈다고 보고합니다. 작은 수정에서는 목표가 요청 문장 안에 들어가서 이 빈틈이 안 보입니다.

**독립 검토가 정확한 입력에 결박된다는 것.** 운영 변경 전에 구현자와 독립된 검토자가 정확한 diff·명령·런북·롤백을 읽고, 그 해시들을 영수증에 묶습니다. 하나라도 바뀌면 판정이 무효입니다. 결박되지 않은 검토는 이전 버전에 대한 의견입니다.

**데이터베이스 방어가 3층이고 진짜 보장은 권한 분리라는 것.** 정규식 내용 검사는 새는 보조 수단입니다. 권한 분리가 켜지기 전에는 유일한 방벽이 새는 것이고, 그 사실을 "보호되고 있다"로 적으면 안 됩니다.

`.agents/context/development-method.yaml` 로 넣었습니다.

## 남은 경계

**독립 교차 검수는 여전히 `NOT_RUN` 입니다.** 이 문서는 실증 프로젝트를 직접 조사한 1차 검수이며, 독립된 외부 모델의 교차 검수를 대신하지 않습니다.

**운영 배포 계약은 아직 활성 어댑터에서 실행되지 않았습니다.** 현재 예제 어댑터는
비활성 placeholder이므로 실제 배포 성공을 주장하지 않습니다. `execution.yaml` 은
무엇을 요구하는지 정했고, 첫 활성 어댑터가 그 명령들을 실제로 구현하기 전까지는
운영 계약 준수를 증명하지 않습니다. 첫 활성 어댑터가 이 계약의 진짜 시험입니다.

**공개 전환 조건은 그대로입니다.** 현재 트리와 도달 가능한 전체 이력을 다시 검사하고 소유자가 정확한 후보 커밋 SHA 를 승인해야 합니다.
