# 요청 수신자와 승인·실행 준비

## 사용 사례와 적용 범위

검토자가 실행안 확인 요청을 받은 뒤 다른 사람이 같은 스레드에 말을 남긴다.
후속 요청은 원래 검토자에게 가야 한다. 이미 같은 범위를 승인한 사람에게
봇의 도구·백업·검토 준비를 이유로 다시 승인을 요구해서는 안 된다.

이 변경은 두 프로파일의 공통 협업 계약과 어댑터 정책 검증을 보강한다.
직접 영향은 어댑터 validator, 공통 계약, 순수 수신자 선택 함수다. 의존하는
메시징 호스트는 새 정책을 명시적으로 채택해야 한다. 공유 런타임·DB·큐를
이 변경으로 수정하지 않는다. 실제 발송·승인 소비·업무 상태 전이는 호스트의 책임이다.

## 어댑터와 호스트 계약

`team_policy.assignment.unanswered_thread_recipient`는 다음 값을 받는다.

| 값 | 용도 |
|---|---|
| `last_human_in_thread` | 기존 어댑터와 호환되는 일반 미응답 스레드 정책 |
| `request_recipient_then_last_human` | 검증된 요청 수신자 우선. 활성 요청이 없는 스레드만 마지막 등록 발언자 사용 |

`scripts/lib/request-recipient.mjs`의 `selectRequestRecipient`는 두 정책의
호스트 구현을 위한 순수 계약 함수다. **설정의 validator 통과만으로 발송 경로가
연결되지는 않는다.** 메시징 런타임은 패키지에서 이 계약을 구현하거나 이 함수를
호출하고, 실제 주기 실행에서 대상·연락 시간·발송 결과를 검증한 뒤 채택해야 한다.
기존 예제의 정책은 자동 변경하지 않는다. 새 정책 이름을 모르는 오래된 validator는
거절하므로 소비자가 지원 버전을 먼저 고정해야 한다.

입력은 `policy`, `context`, `request`, `registeredHumans`, `lastHuman`, `now`,
`workQueued`, `closed`, `held`다. `context`와 요청의 `project`, `workItem`, `thread`,
`requestId`가 정확히 같아야 한다. 호스트가 정규화한 저장소 포함 workItem과
현재 활성 요청 ID를 사용한다. 요청은 `state: pending`, 등록된 사람의 `recipient`,
`decision`, `planRef`, `replyTemplate`, 시간대가 있는 미래 `expiresAt`을 갖는다.
`now`는 호스트가 읽은 현재 시각의 epoch milliseconds다.

`registeredHumans`는 인증된 호스트가 해당 프로젝트의 활성 사람만 투영한 별칭 목록이다.
원본 채팅, 봇 요약, 임의 도구 인수로 이 등록부나 요청을 만들지 않는다. 호스트는
큐·이슈·스레드·등록부·요청을 새로 조회하고 조회 실패면 호출/발송을 중지한다.
발송 직전에도 같은 활성 요청 ID와 증거, 연락 시간 및 대기 상태를 재확인한다.
함수는 호출자 인증, 동시성 잠금, 알림 권한 또는 승인 권한을 대신하지 않는다.

반환값은 `ask`와 수신자 별칭, `none`, 또는 `agent_repair`와 원인이다.
유효한 명시 요청이 있으면 두 정책 모두 그 상대를 보존한다. 요청이 null·잘못된 형식·
만료·취소·다른 이슈·스레드·요청 ID이면 다른 사람으로 대체하지 않는다.
두 정책 모두 활성 requestId만 있고 요청 객체가 없으면 조회 누락으로 판정한다.
진행할 봇 작업이 큐에 있거나 이슈가 닫혔거나 호스트가 명시적으로 `held: true`를 제공하면 재촉하지 않는다. `held`의 기본값은 false이며 문구로 추론하지 않는다.

`agent_repair`는 봇의 증거 확인·요청 정리 작업이다. 사람 승인이나 운영 쓰기를
허가하지 않고 기존 대기를 임의로 덮어쓰지도 않는다. 잘못된 사람 대기를 발견한
호스트는 현재 요청 ID에 결박된 검토 결과로만 상태를 갱신한다.

## 승인 보존

승인 의도와 실행 준비 상태는 별개다. 같은 작업·대상·효과의 유효한 승인을 보존하고
봇이 실행안, 검증, 백업·복구, 정확 명령 및 필수 검토를 준비한다. 준비가 부족하면
그 작업을 이어간다. 준비 완료까지 봇 작업을 사람의 승인 대기로 기록하지 않는다.

인증된 권한자가 구체적으로 검토된 실행안에 답한 짧은 `승인`도 그 실행안에 연결할
수 있다. 임의 채팅 문구를 권한으로 바꾸는 것은 아니다. 실제 실행은 기존 승인
증거의 대상·리비전·유효기간·단회 소비 조건 및 모든 실행 게이트를 그대로 만족해야 한다.
짧은 답변을 해석하는 새 승인 파서를 만들지 않는다. 실제 배포 승인 조건은 아래 어댑터 정책으로 명시한다.

## 위험에 따른 배포 승인 정책

`team_policy.approval.production_deploy`는 기존 `required`를 기본으로 유지하고,
호스트가 명시적으로 `high_risk_only`를 채택할 수 있다. 후자는
`guards.production_requires_issue_approval: false`와 함께 설정한다. 이 boolean은
매 배포의 일괄 승인 요구 여부이며, 높은 위험의 승인을 없애는 설정이 아니다.
`high_system_risk: required`와 배포 실행 역할·계정 경계는 그대로 유지한다.

조건부 정책의 실제 policy-guard는 `deployment_review`에 실행 revision,
`system_risk`·`traffic_risk`(low/medium/high), `human_only_decision` boolean,
`reviewed_by`, `review_ref`, `rollback_artifact`, `verification_ref`를 요구한다.
검토자는 등록된 release owner 역할이며 실행자·이슈 담당자와 독립돼야 한다.
호스트는 인증된 검토 결과를 정확한 이슈·실행안에 결박해 evidence를 생성한다.
원본 채팅이나 backend가 자기 위험을 선언한 값을 검토 증거로 쓰지 않는다.

시스템·트래픽 위험이 모두 비고위험이고 사람 고유 판단도 없으면 추가 사람 승인 없이
허가된 배포 명령으로 진행한다. 사용자 영향이 낮거나 긴급해도 같은 규칙이다.
어느 한 위험이 높거나 사람 판단이 있으면 기존 revision·승인자 검증을 통과해야 한다.
알 수 없는 위험이나 검토·백업 누락은 에이전트가 보완할 실행 준비 결함이다.
이 guard는 기록 결박을 검사하며 실제 검토·백업·서비스 반영 검증은 호스트 실행기가 한다.
일반 dev 병합·배포에는 권한 있는 integrator의 검토·검증을 요구하며 별도 소유자 답변을 요구하지 않는다.

새 범위·위험, 철회·만료, 아직 결정되지 않은 사람 판단에만 새 요청을 만든다.
대상, 결정할 내용, 작업·환경·범위, 검토 실행안 링크, 답변 양식, 기한을 한 요청에
담는다. 예: `승인 example/project#7 plan-a / 보류 이유`. 요청 기한 만료는 봇의
요청 재검토 사유이며, 별도 유효기간을 가진 기존 운영 승인까지 자동 취소하지 않는다.

게이트웨이 연결·답변 게시만으로 업무 정상이라 판단하지 않는다. 보고 뒤 후속 작업
누락, 봇 준비 부족을 이유로 승인 거부, 수신자·답변 양식 없는 요청은 별도 업무 검토
신호다. 이 신호는 자동 승인이나 무조건적인 실행 지시가 아니다.

## 검증과 복구

- `npm run test:adapter-contract`: 두 프로파일의 새 정책·기존 정책 허용 및 알 수 없는 정책 거절.
- `npm run test:request-recipient`: 지정 수신자, 오래된/다른 요청, 누락·취소·만료,
  잘못된 등록부, 큐 작업, 종료 이슈 및 소유자 fallback 부재를 확인한다.
- `npm test`: 기존 정책 guard·backend bridge·게이트웨이 selftest와 전체 공개 안전성 검사.
- 배포를 동반하지 않는 소스 변경이다. 되돌릴 때는 이 변경 커밋을 revert하고 검사를
  실행한다. 이미 새 정책을 채택한 호스트는 소비자 설정과 코드의 지원 버전을 함께
  맞추며, 살아 있는 지정 요청을 구형 경로로 조용히 넘기지 않는다.

## 잘못된 보류를 정리하는 호스트 계약

봇 요약이나 `승인 / 보류 사유` 답변 양식에 보류라는 단어가 있다고 작업을 중단하지 않는다.
승인 요청을 그만하라는 지시와 작업을 멈추라는 지시도 구분한다. 위 수신자 함수는 호스트의
명시적 held 상태에 따라 알림만 억제하며, 보류의 정당성이나 해제를 판정하지 않는다.

기존 보류를 해제하기 전에는 정본 이슈·스레드에서 인증된 사람의 원문과 편집을 조회하고,
원래 실행의 적용·미적용·미확인 효과를 대조한다. 과거 보류가 누락될 수 있는 잘린 기록은
해제 근거가 아니다. 기록 직전에 원문과 최신 수신 메시지·대기 상태를 다시 확인한다.
봇 글을 사람 증거로 사용하거나 자료 준비 누락을 사용자에게 넘기지 않는다.

이전 대기·요청과 검토 근거를 보존한다. 실제 사람 보류는 새 질문 없이 유지하고 미확인
효과도 남긴다. 잘못된 보류를 해제해도 새 실행 권한은 생기지 않는다. 실패하거나 결과가
누락된 검토를 자동 재귀 실행하지 않고 에이전트 대조 대상으로 기록한다. 이는 호스트
구현 의무이며 이 저장소의 선언·수신자 검사만으로 실제 채택 완료를 주장하지 않는다.
