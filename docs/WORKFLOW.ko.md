# 팀 개발 운영 절차

## 개발자

1. GitHub에서 이슈를 만들거나 배정받습니다. 무엇을 바꾸는지, 어떻게 확인하면 되는지를 먼저 적습니다.
2. 개인 계정으로 개발 서버에 SSH 접속하고 개인 작업공간으로 이동합니다.
3. 저장소를 최신화한 뒤 `issue/이슈번호-짧은이름` 브랜치를 만듭니다.

   ```bash
   cd ~/프로젝트이름
   git fetch origin
   git switch dev
   git pull --ff-only origin dev
   git switch -c issue/123-banner-change
   ```

4. 그 디렉터리에서 `codex` 또는 `claude`를 실행하고 다음처럼 요청합니다.

   > 이슈 123을 읽고 이 작업공간 규칙에 따라 구현해줘. 운영 배포와 DB 변경은 하지 말고, 테스트 결과와 dev 병합 요청 문안을 만들어줘.

5. 결과를 직접 확인하고 커밋을 푸시합니다. 이슈에 커밋, 테스트 결과, 확인 방법, 되돌리는 방법을 적고 dev 병합을 요청합니다.

   ```bash
   git status
   npm test
   git add <확인한-파일>
   git commit -m "fix: 이슈 123 배너 변경"
   git push -u origin issue/123-banner-change
   ```

   프로젝트의 실제 검증 명령은 `projects/<프로젝트>/project.yaml`의 `commands.validate`를 따릅니다. 위 `npm test`는 예시입니다.

## 이슈에 남길 dev 병합 요청 예시

> 이슈 #123 작업을 완료했습니다. 개인 브랜치 `issue/123-banner-change`, 커밋 `<SHA>`입니다. `<검증 명령>`을 실행해 통과했습니다. dev에서는 `<확인 절차>`로 확인해 주세요. 문제가 생기면 `<되돌리기 절차>`로 복구할 수 있습니다. dev 병합과 개발 환경 배포를 요청합니다.

## dev 병합 담당자

1. 이슈의 완료 조건과 검증 결과를 확인합니다.
2. 변경을 검토하고 `dev`에 병합합니다.
3. 개발 환경에 배포한 뒤 환경 주소, 병합 SHA, 확인 결과를 같은 이슈에 기록합니다.
4. 실패하면 병합 전 상태로 되돌리고 이슈를 개발 단계로 돌립니다.

## 검수·운영 배포 담당자

1. dev 배포 요청이 오면 Discord 메시지만 보지 말고 GitHub 이슈를 엽니다.
2. 이슈에 적힌 확인 절차로 개발 환경을 검수합니다.
3. 승인 여부를 이슈에 명시합니다.
4. 승인된 정확한 SHA만 운영에 배포합니다.
5. 배포 결과와 운영 확인, 되돌리기 기준을 이슈에 기록한 뒤 닫습니다.

## 금지 사항

- 이슈 없이 작업하거나 배포하지 않습니다.
- 개인 브랜치에서 운영 서버로 직접 배포하지 않습니다.
- Discord 요청만으로 병합·배포·DB 변경 권한이 생기지 않습니다.
- 비밀번호, 토큰, 개인 ID, 서버 주소를 이슈나 저장소에 적지 않습니다.
